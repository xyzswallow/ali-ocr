# 多用户与数据隔离改造方案

## Summary

给「票识」加上账号体系，把当前单租户的发票识别工具改造成多用户平台，每个用户只能看到并操作自己的识别记录。

核心设计取向（对应已确认的决策）：

- **自建凭据登录**：邮箱 + 密码，密码用 Node 内置 `crypto.scrypt` 派生（OWASP 推荐的 KDF 之一），不引入 bcrypt/argon2 原生依赖。
- **数据库会话（opaque token）**，不用 JWT：cookie 里放 32 字节随机 token，库里只存它的 SHA-256，可随时吊销。省掉 `SESSION_SECRET` 和 `jose` 依赖。
- **开放注册**：任何人可自助注册，注册入口在悬浮弹窗内。
- **存量数据归属管理员**：迁移时按环境变量创建 admin 账号，把已有 `invoice_records` 全部划归该账号。
- **首页公开 + 按需登录**：不做全站强制跳转，工作区未登录也能浏览；只在用户点「开始识别」时弹出悬浮登录框，登录成功后原地续跑本次识别。会话校验和 `user_id` 过滤全部下沉到贴近数据源的 DAL 与 SQL 里。

安全目标：修掉当前三个 API 路由完全无鉴权、以及 `/api/records/[id]` 凭 UUID 即可读他人发票的 IDOR 漏洞。

## Proposed Changes

### 1. 数据库层

#### 1.1 `src/lib/db.ts` — 加入轻量迁移机制与两张新表

**为什么**：现有 `CREATE TABLE IF NOT EXISTS` 无法给已存在的 `invoice_records` 加列。用 SQLite 内置 `user_version` pragma 做版本号，零依赖。

**怎么做**：把 `openDatabase()` 中的 `database.exec(...)` 替换为 `migrate(database)` 调用，迁移逻辑：

```ts
function migrate(database: Database.Database) {
  const current = database.pragma("user_version", { simple: true }) as number;

  if (current < 1) {
    // v1：原始 schema（幂等，覆盖新库与已有库）
    database.exec(`
      CREATE TABLE IF NOT EXISTS invoice_records (...原样保留...);
      CREATE INDEX IF NOT EXISTS idx_invoice_records_created_at ON invoice_records(created_at DESC);
    `);
    database.pragma("user_version = 1");
  }

  if (database.pragma("user_version", { simple: true }) < 2) {
    database.exec(`
      CREATE TABLE users (
        id TEXT PRIMARY KEY,
        email TEXT NOT NULL UNIQUE,          -- 存小写规范化后的邮箱
        password_hash TEXT NOT NULL,         -- scrypt: salt:hash（hex）
        display_name TEXT NOT NULL,
        role TEXT NOT NULL DEFAULT 'member' CHECK(role IN ('member','admin')),
        created_at TEXT NOT NULL
      );
      CREATE TABLE sessions (
        id TEXT PRIMARY KEY,                 -- token 的 SHA-256（hex），明文只存在 cookie 里
        user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
        expires_at TEXT NOT NULL,
        created_at TEXT NOT NULL
      );
      CREATE INDEX idx_sessions_user_id ON sessions(user_id);

      ALTER TABLE invoice_records ADD COLUMN user_id TEXT REFERENCES users(id) ON DELETE CASCADE;
      CREATE INDEX idx_invoice_records_user_created
        ON invoice_records(user_id, created_at DESC);
    `);
    database.pragma("user_version = 2");
  }
}
```

设计说明：

- `user_id` 声明为**可空**（SQLite 无法给已有表加 `NOT NULL` 且无默认值的列）。约束由应用层保证：所有写入路径必带 `userId`；所有读取路径必带 `user_id = ?`，NULL 行天然不可见。
- 需在 `openDatabase()` 中补 `database.pragma("foreign_keys = ON")`，否则 `ON DELETE CASCADE` 不生效（SQLite 默认关闭）。
- `sessions.id` 存哈希而非明文 token：库泄露时攻击者无法直接冒充会话。

#### 1.2 `src/lib/db.ts` — 现有函数全部加上用户维度

| 函数 | 新签名 | 改动 |
| --- | --- | --- |
| `createInvoiceRecord` | `(userId: string, file: File)` | INSERT 增加 `user_id` 列 |
| `completeInvoiceRecord` | `(userId: string, id, requestId, data, rawResponse)` | `WHERE id=? AND user_id=?` |
| `failInvoiceRecord` | `(userId: string, id, message)` | `WHERE id=? AND user_id=?` |
| `listInvoiceRecords` | `(userId: string, limit = 10)` | `WHERE user_id=? ORDER BY created_at DESC LIMIT ?` |
| `getInvoiceRecord` | `(userId: string, id: string)` | `WHERE id=? AND user_id=?` → 越权直接返回 `null`（表现为 404，不泄露存在性） |

`userId` 一律作为**第一个参数**，形成统一约定：看到调用点没传 userId 就是 bug。`Row` interface 增加 `user_id: string | null`（`summary()` 不暴露它，`InvoiceRecordSummary` 保持不变，避免把内部标识发到前端）。

更新语句同时带 `user_id` 而非只带 `id`：虽然 id 是服务端刚生成的 UUID，但保持「所有 SQL 都带 user_id」的铁律比省一个条件更有价值。

#### 1.3 新建 `src/lib/users.ts` — 用户与会话的数据访问

**为什么**：把认证相关的表操作从发票逻辑里分开，`db.ts` 只保留连接与发票记录。

导出：

```ts
export const SESSION_COOKIE = "ali_ocr_session";
const SESSION_TTL_MS = 7 * 24 * 60 * 60 * 1000;   // 7 天

// scrypt: N=16384(cost 参数用 Node 默认), keylen=64, 随机 16 字节 salt
function hashPassword(password: string): string           // 返回 "saltHex:hashHex"
function verifyPassword(password: string, stored: string): boolean  // timingSafeEqual 比较

export function createUser(email: string, password: string, displayName: string, role?: "member" | "admin"): User
export function findUserByEmail(email: string): UserWithHash | null
export function findUserById(id: string): User | null
export function countUsers(): number

export function createSession(userId: string): { token: string; expiresAt: Date }
export function findSessionUser(token: string): User | null   // 校验哈希 + 未过期，过期则顺手删除
export function deleteSession(token: string): void
export function deleteExpiredSessions(): void
```

要点：

- 邮箱统一 `trim().toLowerCase()` 后存取，避免大小写重复注册。
- `token` = `randomBytes(32).toString("base64url")`；库里键为 `createHash("sha256").update(token).digest("hex")`。
- `verifyPassword` 用 `timingSafeEqual` 防时序侧信道。
- `createUser` 捕获 UNIQUE 约束冲突，抛出可识别的 `AuthError`（见 1.4），路由层转成「该邮箱已被注册」。
- **不做滑动续期**：Next.js 16 中 RSC 渲染期间不能写 cookie，跨请求续期只能在 Server Action / Route Handler 里做，收益不抵复杂度。7 天到期重新登录。

#### 1.4 新建 `src/lib/auth.ts` — DAL（Data Access Layer）

**为什么**：Next.js 官方推荐的模式——把授权检查集中到一处，禁止各处自行拼装。

```ts
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";

export class AuthError extends Error {}           // 认证/注册的可展示错误

// 只读会话，不跳转。首页与 Route Handler 都用它。
export const getCurrentUser = cache(async (): Promise<User | null> => {
  const token = (await cookies()).get(SESSION_COOKIE)?.value;
  return token ? findSessionUser(token) : null;
});

// Route Handler 专用：返回 user 或已构造好的 401 Response。
export async function requireApiUser(): Promise<{ user: User } | { response: NextResponse }>
```

不提供 `requireUser()` 这类「无会话即 redirect」的辅助函数：页面侧不再有强制跳转的场景，登录由客户端弹窗触发。

`cache()` 包裹使同一请求内多次调用只查库一次（React 的 request-scoped 记忆化）。

`setSessionCookie(token, expiresAt)` / `clearSessionCookie()` 也放这里，统一 cookie 选项：

```ts
{ httpOnly: true, secure: process.env.NODE_ENV === "production",
  sameSite: "lax", path: "/", expires: expiresAt }
```

`sameSite: "lax"` 而非 `strict`：保证从外部链接跳回时仍是登录态，同时仍能防御跨站 POST。

### 2. 认证界面与 Server Actions

#### 2.1 登录入口形态：悬浮弹窗，不做独立路由

不新建 `/login`、`/signup` 页面。登录/注册合并为一个悬浮弹窗组件，由工作区在需要身份时挂载，避免用户为了试用而先被赶去注册。

#### 2.2 新建 `src/lib/actions/auth.ts` — Server Actions

**为什么**：官方推荐用 Server Action 处理登录/注册表单，天然防 CSRF（Next.js 内置校验 Origin），无需额外 API 路由。

```ts
"use server";
export type AuthFormState = { error?: string; ok?: boolean };

export async function loginAction(_prev: AuthFormState, formData: FormData): Promise<AuthFormState>
export async function signupAction(_prev: AuthFormState, formData: FormData): Promise<AuthFormState>
export async function logoutAction(): Promise<void>
```

行为细节：

- Zod v3 校验（项目已有 zod ^3.25）：email 格式、密码 ≥ 8 字符、`displayName` 1–40 字符。
- **登录失败统一返回「邮箱或密码不正确」**，不区分「用户不存在」与「密码错」，避免账号枚举。
- 用户不存在时也执行一次 `hashPassword` 空跑，抹平时序差异。
- 登录/注册成功后建会话并 `return { ok: true }`——**不 redirect**。弹窗里要原地关闭并续跑识别，跳转会丢掉用户已选的文件；由客户端监听 `ok` 后 `router.refresh()` 拿到新的会话态。
- `logoutAction` 删库里的 session 行 + 清 cookie + `redirect("/")`。
- 校验失败通过返回值传给 `useActionState`，不抛异常。

#### 2.3 新建 `src/components/auth-dialog.tsx`

一个客户端组件，内部维护 `mode: "login" | "signup"` 并用按钮切换（不再是跨页面的 `Link`）。表单主体 `AuthPanel` 用 `key={mode}` 挂载，切换模式时自动重置 `useActionState` 的残留错误。`useFormStatus` 的 pending 态禁用提交按钮。

弹窗外壳：`fixed inset-0` 半透明遮罩 + 居中卡片，点遮罩或按 Esc 关闭，卡片内 `stopPropagation`；带 `role="dialog"` 与 `aria-modal="true"`。

样式沿用现有设计语言（扁平、无圆角、主色 `#087f72`、深色 `#172024`、边框 `#d9dfe2`、次要文字 `#758086`），与 [invoice-workspace.tsx](file:///Users/xue/Desktop/code/ali_ocr/src/components/invoice-workspace.tsx) 保持一致；顶部沿用 `ScanLine` 图标与「票识」标题。

## Assumptions & Decisions

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 认证实现 | 自建凭据（用户已确认） | 依赖轻、完全可控，与现有 better-sqlite3 直接契合 |
| 密码哈希 | Node 内置 `crypto.scrypt` | 免装 bcrypt/argon2 原生模块（后者在部署时常有编译问题）；scrypt 是 OWASP 认可的 KDF |
| 会话形式 | 数据库 opaque token | 可即时吊销、无需管理签名密钥；单机 SQLite 场景下查库开销可忽略。JWT 的免查库优势在此无价值 |
| 会话有效期 | 7 天固定，不滑动续期 | Next.js 16 RSC 渲染期不能写 cookie，滑动续期需额外机制，收益不足 |
| 注册开放性 | 开放注册（用户已确认） | —— |
| 首个用户角色 | `member`，管理员由种子脚本建 | 「首个注册者自动成为 admin」在开放注册下是抢注风险 |
